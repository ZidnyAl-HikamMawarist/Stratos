# Stratos Security Test Plan
**Version:** 1.0.0  
**Purpose:** Turn security requirements into testable controls. This plan does not certify the application as secure.

## Severity and handling
- **Critical/High:** block milestone or release until fixed or explicitly accepted after review.
- **Medium:** document owner, mitigation, and due milestone.
- **Low:** record and prioritize according to impact.
- Never place real tokens, cookies, API keys, or private project contents in test fixtures.

## Test matrix

| ID | Threat / scenario | Expected control | Verification |
|---|---|---|---|
| SEC-001 | Renderer attempts arbitrary Node access | Node integration disabled; narrow preload API | Inspect BrowserWindow config and attempt prohibited access |
| SEC-002 | Renderer sends unknown IPC channel | Allowlist rejects it | Automated negative IPC test |
| SEC-003 | IPC sender is unexpected window/frame | Sender validation rejects it | Unit/integration test with invalid sender |
| SEC-004 | Malicious website requests local router | Auth required; origin/host defenses; loopback only | Integration test from disallowed origin and unauthorized client |
| SEC-005 | DNS rebinding/Host confusion | Host and origin handling does not trust arbitrary hostnames | Security test against unexpected Host values |
| SEC-006 | API key appears in error/log | Redaction before persistence/display | Seed fake canary secret and scan logs/diagnostics |
| SEC-007 | Token stored in ordinary DB/config | Secret-store boundary enforced | Inspect DB/config after adding a test credential |
| SEC-008 | Path traversal (`../`) | Canonicalized path remains within root | Unit tests with traversal paths |
| SEC-009 | Symlink points outside workspace | Denied by default or explicit approval required | Windows filesystem integration test |
| SEC-010 | Agent proposes destructive command | Confirmation/policy gate applies | Simulated command proposal |
| SEC-011 | Provider response contains prompt injection | Treat response/project content as untrusted; tools still validate/authorize | Agent test fixture with hostile instructions |
| SEC-012 | Remote content loaded in privileged window | Prohibited or isolated with no privileged bridge | Inspect window/navigation policy and tests |
| SEC-013 | Unexpected navigation/window creation | Blocked or opened externally only after URL validation | Integration test |
| SEC-014 | Database migration fails | No silent deletion; clear recovery path | Inject migration failure in test DB |
| SEC-015 | PTY process remains after app exit | Lifecycle cleanup or visible recovery | Start harmless long-running process, close app, inspect process |
| SEC-016 | Logs contain prompt/source code by default | Minimal logging; content logging opt-in | Inspect records generated by default |
| SEC-017 | Dependency has known high-severity advisory | Review and mitigate before release | Dependency audit and documented result |
| SEC-018 | Installer/build artifact tampering risk | Release artifact and distribution process reviewed | Document signing/checksum strategy appropriate to distribution |

## Required Electron configuration review

Before release, verify against the current official Electron security guidance:
- Current supported Electron release and patch level.
- `nodeIntegration: false`.
- `contextIsolation: true`.
- Renderer sandbox enabled; exceptions justified and reviewed.
- Restrictive Content Security Policy.
- No disabling of `webSecurity`.
- Navigation, window creation, and permissions constrained.
- Preload exposes explicit methods, not generic IPC senders.
- IPC sender and arguments validated.
- Untrusted remote content is never loaded in a privileged renderer.
- External URL opening validates protocol and destination.

Official reference: https://www.electronjs.org/docs/latest/tutorial/security/

## Test execution record template

For each run, record:
- Date and Windows version
- App commit/version
- Test ID and steps
- Expected result
- Actual result
- Pass/Fail/Blocked/Not run
- Evidence (redacted log, screenshot, or test output)
- Severity and follow-up issue

A requirement is not verified merely because the code appears to implement it. Run the test or clearly mark it as unverified.
